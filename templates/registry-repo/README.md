# nParse+ plugin registry

The curated catalogue behind **nParse+ → Settings → Plugins → *Browse
registry…***. This repository *is* the registry: there is no server, no
database and no API. A single reviewed [`index.json`](index.json) is published
as a static file by GitHub Pages, and the app fetches it.

- **Index:** <https://prokopto-dev.github.io/nparseplus-plugins/index.json>
- **Schema:** [`schema/index-v1.schema.json`](schema/index-v1.schema.json)
- **Ownership record:** [`owners.json`](owners.json)
- **Submitting a plugin:** [CONTRIBUTING.md](CONTRIBUTING.md)

## For users

nParse+ points here out of the box — you do not have to configure anything.
Open Settings → Plugins → *Browse registry…*, and the app fetches the index,
hides entries that are not compatible with your nParse+ / SDK version, and
offers one-click installs.

To use a different (or a private) catalogue, set `plugins.registry_url` in
your `settings.json` to any https URL serving a document in this format. If
the registry is unreachable, Browse simply says "Registry unavailable" —
installing from a file or a URL, and the plugins folder, keep working.

## Trust model — read this

**A registry listing is a curation signal, not a safety guarantee.** Plugins
are ordinary in-process Python: they run with the full permissions of nParse+,
which means the full permissions of your user account. Install code you trust.

What the registry actually guarantees:

- **The bytes are pinned.** Each entry records the sha256 of the exact release
  artifact a maintainer reviewed. nParse+ hashes the download and refuses it —
  *before extraction, before any of its code runs* — unless the bytes match.
  The URL is transport; the hash is the security boundary. An author cannot
  swap the artifact behind an already-listed URL without a new PR and a new
  review.
- **A human looked at it.** Every entry got here through a pull request that a
  maintainer reviewed and merged. Expect them to read your source.
- **Ids are first-come and permanent**, recorded in `owners.json` and enforced
  in CI, so a listing cannot be quietly taken over by someone else.

What it does not guarantee: that a reviewed plugin is bug-free, that a later
version is as benign as the one first reviewed, or that review catches
deliberately obfuscated behaviour. nParse+ still shows its first-load consent
dialog for registry installs — that is your decision to make, and curation
does not replace it.

Automated checks run on every submission (JSON-Schema validity, id format and
uniqueness, https-only URLs, hash format, ownership, and a re-download that
confirms the artifact really hashes to the recorded value). They are a filter
that saves reviewers time; the merge is the trust boundary.

## Reporting a problem

Open an issue — or, for anything you believe is actively malicious, contact
the maintainers privately via the security policy of
[prokopto-dev/nparse-plus](https://github.com/prokopto-dev/nparse-plus) rather
than filing a public issue. Delisting is a PR that removes the entry from
`index.json`; the `owners.json` claim stays, because ids are never recycled.

## Repository layout

| Path | What it is |
| --- | --- |
| `index.json` | The published catalogue. The only file the app reads. |
| `owners.json` | plugin id → GitHub handles. Makes "first come" checkable. |
| `schema/index-v1.schema.json` | Generated from the app's pydantic models — do not hand-edit. |
| `.github/workflows/validate-index.yml` | The submission checks. |
| `SETUP.md` | Maintainer notes: standing this repository up. |

The schema is generated by `tools/gen_registry_schema.py` in
[prokopto-dev/nparse-plus](https://github.com/prokopto-dev/nparse-plus) from
`nparseplus.core.plugins.registry`, which is the source of truth for the wire
format. Copy an updated schema in from there rather than editing it here.

## Format

See the [registry documentation](https://prokopto-dev.github.io/nparse-plus/plugins/registry/)
for the specification. In short:

```json
{
  "schema_version": 1,
  "plugins": [
    {
      "id": "merchant-prices",
      "name": "Merchant Prices",
      "description": "Tracks your WTS auctions with PigParse price history.",
      "author": "someone",
      "homepage": "https://github.com/someone/nparse-merchant-prices",
      "latest": {
        "version": "1.2.0",
        "url": "https://github.com/someone/nparse-merchant-prices/releases/download/v1.2.0/merchant_prices.zip",
        "sha256": "<64 lowercase hex characters>",
        "requires_sdk": ">=1.0,<2",
        "min_app_version": "1.15.0"
      }
    }
  ]
}
```

Only `latest` is carried per plugin: the registry lists the current reviewed
release, not a version history. `min_app_version` is optional; omit it unless
your plugin needs a specific nParse+ version. A `schema_version` newer than an
app understands makes it say "update nParse+" rather than misread the index —
so bumping it is a breaking change for every older client.
